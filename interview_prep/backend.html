backend/server.py

Main purpose: server.py is the entry point and the "traffic controller" (router) for your entire Tornado backend application. When you run the backend, this is the script that actually starts the server and listens for requests. 
def make_app(debug: bool = False) -> tornado.web.Application:
    return tornado.web.Application(
        [
            (r"/api/health", HealthHandler),
            (r"/api/v1/competition/([^/]+)/table", CompetitionTableHandler),
            (r"/api/v1/match/([^/]+)/facts", MatchFactsHandler),
            (r"/static/(.*)", tornado.web.StaticFileHandler, {...}),
            (r"/example", ExamplePageHandler, {...}),
            (r"/config", ConfigPageHandler, {...}),
        ],
        debug=debug,
    )

Here is a breakdown of what the code does:

First, it imports all the concrete handlers from backend/handlers and sets up a few simple handlers like HealthHandler for health checks, as well as handlers to serve the static HTML pages.

The core of this file is the make_app() function. This creates the actual Tornado application object and defines the routing table. It uses Regular Expressions to map specific URL patterns to the Handler classes. For example, it maps /api/v1/match/123/facts to the MatchFactsHandler.

Why this design is good: It keeps the prototype completely self-contained. It serves both the API and the static assets from the same process, which makes the system incredibly easy to run and demonstrate without needing a complex proxy setup.

backend/handlers/base.py

Main purpose: This file defines a BaseHandler class that acts as the foundation for all other API endpoints. It provides reusable methods so you don't have to rewrite logic in every single endpoint. 
class BaseHandler(tornado.web.RequestHandler):
    def apply_cache_headers(self, ttl: int) -> None:
        self.set_header("Cache-Control", f"public, max-age={ttl}")

    async def load_mock_json(self, filename: str) -> Any:
        await asyncio.sleep(self.MOCK_IO_DELAY_SECONDS)
        return await asyncio.to_thread(self._read_json_file, self.mock_data_dir / filename)

    def write_envelope(self, *, data, error=None, status_code: int = 200, cache_ttl: int = 0) -> None:
        payload = {"meta": {...}, "data": data, "error": error}
        self.write_json(payload, status_code=status_code)

Here is a breakdown of what the code does, section by section:

CORS & Caching: Because every handler inherits from BaseHandler, they all behave consistently. It sets default headers to allow Cross-Origin Resource Sharing (CORS), ensuring your frontend can communicate with the API. It also provides apply_cache_headers() to control browser caching.

Mock Data Loading: Because this is a prototype, load_mock_json() simulates real-world conditions. It intentionally delays the response by 50ms (simulating network/DB latency) and reads the JSON file in a separate thread to keep the server asynchronous and responsive.

Standardized Responses: The write_envelope() and write_error_envelope() methods are an excellent professional practice. Instead of sending back raw arrays, they force every API response to use a consistent envelope structure (meta, data, error).

Why this matters: It gives the API one unified personality. That makes the frontend much simpler to build and test because all endpoints follow the exact same rules.

backend/handlers/state.py

Main purpose: Serves the current match state, which is the most important live control payload for the frontend. 
class MatchStateHandler(BaseHandler):
    CACHE_TTL = 5
    REQUIRED_FIELDS = {"phase", "clock", "home_score", "away_score", "home_team", "away_team"}

    async def get(self, match_id: str) -> None:
        self.apply_cache_headers(self.CACHE_TTL)
        payload = await self.load_mock_json(f"match_{match_id}_state.json")
        ...
        self.write_envelope(data=payload, error=None, cache_ttl=self.CACHE_TTL)

How it works:

Right away, it sets a very short CACHE_TTL of 5 seconds because this endpoint controls live widget behavior and needs to stay fresh.

It calls the inherited load_mock_json() to fetch the file. It uses robust error handling here: if the file is missing, it sends a structured 404 error envelope; if the JSON is corrupted, it sends a 500 error envelope.

Finally, it validates that crucial fields like phase, clock, and scores actually exist before wrapping the payload in the standard envelope and sending it off.

Why this endpoint matters so much: The frontend relies entirely on this endpoint to update the match header, reveal live-only tabs, detect confirmed lineups, and know when to stop polling at full time.

backend/handlers/table.py

Main purpose: Serves the league table for a competition. 
class CompetitionTableHandler(BaseHandler):
    CACHE_TTL = 300

    async def get(self, competition_id: str) -> None:
        self.apply_cache_headers(self.CACHE_TTL)
        payload = await self.load_mock_json(f"competition_{competition_id}_table.json")
        if not isinstance(payload, list):
            self.write_error_envelope(...)
            return
        self.write_envelope(data=payload, error=None, cache_ttl=self.CACHE_TTL)

How it works:

Unlike the match state, league standings are relatively stable, so this handler uses a much longer TTL of 300 seconds.

It loads the competition-specific table JSON file, performs basic safety checks (ensuring the payload is an array), and then wraps the standings in the standard response envelope.

Why the path shape is good: The routing for this is /competition/:id/table. This clearly scopes the resource to the competition level, rather than being a generic or database-shaped endpoint.

backend/handlers/fixtures.py

Main purpose: Serves fixture or result lists for a competition, demonstrating filtering and limits. 
status = self.get_query_argument("status", default=None)
limit = self.get_query_argument("limit", default="5")

if status is not None and status not in self.VALID_STATUSES:
    self.write_error_envelope(status_code=400, code="invalid_status", ...)
    return

payload = await self.load_mock_json(f"competition_{competition_id}_fixtures.json")
if status is not None:
    payload = [row for row in payload if row.get("status") == status]
payload = payload[:limit_value]

How it works:

It reads optional query parameters (status and limit) and performs strict validation on them. For instance, status must be either 'scheduled' or 'played', and limit must be a positive integer.

After loading the data, it applies light business logic: it filters the array by status if requested, and then slices the array to ensure it only returns the requested number of items.

Why this is a good interview example: It shows input validation, cache reasoning, domain scoping, and business logic all in one compact, easy-to-read handler.

Step-by-step breakdown:

Now that you understand BaseHandler, this is a great example of those foundations at work. It sets a 15-second TTL because facts can include live updates.

Just like fixtures, it reads and strictly validates the category and limit query parameters. If validation fails, it immediately uses the inherited write_error_envelope to return a cleanly formatted JSON error and stops executing.

After fetching the mock data, it filters the facts by the requested category, slices the array, and uses write_envelope to package the final payload.

backend/handlers/xg_race.py

Main purpose: Serves the expected goals (xG) timeline data used to render the live chart. 
REQUIRED_FIELDS = {
    "home_team", "away_team", "timeline_minute",
    "home_xg_cumulative", "away_xg_cumulative",
}

payload = await self.load_mock_json(f"match_{match_id}_xg_race.json")
missing_fields = sorted(self.REQUIRED_FIELDS - payload.keys())
if missing_fields:
    self.write_error_envelope(status_code=500, code="invalid_xg_race_payload", ...)

How it works:

Because this feeds a live chart, it uses a 10-second cache TTL. It loads the JSON and performs a strict validation check to ensure all required timeline and team fields exist before returning the payload.

Important frontend connection: Notice that the backend returns the *entire* xG progression for the match. It's the frontend's job to trim that data down to the current match clock for live display. This separation of concerns keeps the backend handler wonderfully simple.

backend/handlers/squads.py

Main purpose: Serves squad and lineup data for both teams.

        payload = await self.load_mock_json(f"match_{match_id}_squads.json")

        self.write_envelope(data=payload, error=None, cache_ttl=self.CACHE_TTL)

How it works:

It loads the squad data, validates that both "home" and "away" objects exist, and returns them in the standard envelope.

Why this endpoint is more powerful than it looks: This single payload is designed to support several frontend states: pre-match full squads, confirmed starting lineups, and eventually live pitch/event views.

backend/handlers/team_stats.py

Main purpose: Serves aggregate team statistics, utilizing shared logic to support both individual team stats and specific match comparisons. 
class TeamStatsBaseHandler(BaseHandler):
    VALID_SPLITS = {"season", "last_5", "last_10", "home", "away", "live"}

    def validate_split(self, split: str) -> bool:
        ...

    def write_split_payload(self, payload, split: str) -> None:
        ...
        self.write_envelope(data=payload[split], error=None, cache_ttl=self.CACHE_TTL)

How it works:

This introduces a sensible internal abstraction. TeamStatsBaseHandler defines valid stat splits (like 'season' or 'last_5') and centralizes the loading and validation behavior.

Then, both TeamStatsHandler (for /team/:id/stats) and MatchTeamStatsHandler (for /match/:id/team-stats) inherit from this base class to avoid duplicating logic.

Why this is worth highlighting: It shows you know how to structure code cleanly. The abstraction avoids repetition without turning the public API into a vague, untyped mess.
