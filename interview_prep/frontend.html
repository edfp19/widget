frontend/loader.js

Main purpose: this is the widget entry point. It reads the script tag configuration, loads the dependent assets, resolves page context, fetches initial state, mounts the widget container, and starts polling for match pages. 
var context = {
    pageType: pageType,
    matchId: matchId,
    competitionId: competitionId,
    client: normalizeNullableString(dataset.client),
    theme: normalizeString(dataset.theme, DEFAULTS.theme),
    visibleTabs: normalizeTabList(dataset.visibleTabs),
    defaultTab: normalizeString(dataset.defaultTab, DEFAULTS.defaultTab),
    apiBase: normalizeString(dataset.apiBase, resolveDefaultApiBase(node)),
    pollIntervalMs: normalizeInteger(dataset.pollIntervalMs, DEFAULTS.pollIntervalMs)
};

Step by step

  1. It defines default widget settings such as page type, theme, default tab, and poll interval.
  2. It includes helper functions that normalize raw string values from data-* attributes into cleaner JS values.
  3. It derives the static asset base path from the loader script URL so the widget can find its sibling files.
  4. It loads widget.css, renderers.js, canvas_chart.js, and container.js only once, even if the page tried to initialize again.
  5. ContextResolver reads the current script tag and builds the widget context object from its dataset.
  6. validateContext() enforces the page-type rules: match pages need a match ID, competition pages need a competition ID, and homepage embeds must pin one explicitly.
  7. prepareContext() fetches initial match state and squads data so the widget starts with rich context.
  8. boot() wires the whole startup process together: dependencies, context, root, initial state, container creation, tab registration, initial rendering, and polling startup.
  9. If any of that fails, renderBootError() creates a visible error card instead of silently failing.

Why this file is strategically important: this is where the embeddable widget model becomes real. If they ask how a single script tag supports different page types and themes, this is the answer.

Main purpose: defines the WidgetContainer class, which owns the widget shell, tab system, active state, polling lifecycle, and phase transitions.

startPolling() {
    this._pollInterval = global.setInterval(
        () => this.pollMatchState(),
        this.context.pollIntervalMs || 5000

Step by step

  1. The constructor stores the context, creates the root node, adds useful data-* markers, and renders the shell.
  2. renderShell() creates the persistent match header, the tab navigation area, and the content viewport.
  3. updateHeader() updates teams, score, and clock while copying those values into the context object.
  4. registerTab() creates the tab button and panel, stores fetch metadata, and wires click handlers.
  5. refreshTab() manages loading, successful completion, and visible tab-level error states.
  6. initTabs() preloads data, applies phase visibility rules, and activates the right starting tab.
  7. applyPhaseVisibility() hides pre-match or live-only tabs depending on the current phase.
  8. startPolling() and pollMatchState() keep match pages fresh by periodically fetching state.
  9. handlePhaseTransition() switches the widget into the right visual mode as the match progresses.

Why this matters: this file is the runtime brain of the widget. The loader starts the system; the container keeps it alive and correct over time.

frontend/renderers.js

Main purpose: contains the actual rendering logic for each widget view: league table, fixtures, team stats, H2H, facts, squads, and their supporting helpers. 
function renderTeamStats(panel, data, options) {
    panel.innerHTML = [
        '<div class="sr-panel-heading">Team Comparison</div>',
        '<div class="sr-toolbar">...',
        renderStatsBody(data, statKeys)
    ].join('');

    select.addEventListener('change', async function () {
        var response = await global.fetch(options.endpoint + '?split=' + encodeURIComponent(select.value));
        var payload = await response.json();
        renderTeamStats(panel, payload.data, ...);
    });
}

How to think about this file

  1. The top of the file contains utilities like escapeHtml(), formatDate(), and isInPlayPhase().
  2. The next layer contains renderer clusters by feature: table, fixtures, team stats, H2H, facts, and squads.
  3. Each renderer receives a panel and some data, then turns that into DOM content.
  4. Some renderers are mostly static transforms, while others also wire interactive behavior like selectors or filters.

Important renderer groups

  • Table: renders standings plus optional overall, home, and away subviews.
  • Fixtures: renders upcoming fixtures and previous results columns.
  • Team stats: renders split selectors and refreshes data when the user changes split.
  • H2H: renders team summary, recent results, and player-vs-player views.
  • Facts: filters facts, hides future live facts until the clock reaches them, and merges updates during live play.
  • Squads: switches between pre-match squads, confirmed lineups, and live pitch/event views.

Why this matters: this file turns raw API payloads into actual product behavior. It is where most of the user-visible intelligence lives.

frontend/canvas_chart.js

Main purpose: draws the xG race chart using the HTML canvas API instead of a charting library. 
function renderXgChart(panel, data) {
    var canvas = document.createElement('canvas');
    ...
    function draw() {
        var minutes = Array.isArray(data.timeline_minute) ? data.timeline_minute : [];
        var homeSeries = Array.isArray(data.home_xg_cumulative) ? data.home_xg_cumulative : [];
        var awaySeries = Array.isArray(data.away_xg_cumulative) ? data.away_xg_cumulative : [];
        drawStepLine(context, minutes, homeSeries, ..., homeColor);
        drawStepLine(context, minutes, awaySeries, ..., awayColor);
    }
}

Step by step

  1. It creates a canvas element and inserts it into the panel.
  2. The nested draw() function measures the available width and computes chart bounds.
  3. It reads the timeline and cumulative xG arrays from the payload.
  4. It reads theme colors from the widget root CSS variables.
  5. It draws axes and then draws a step line for each team.
  6. If ResizeObserver exists, it redraws the chart when the panel size changes.

Why this was a practical choice: it avoids a heavyweight chart dependency while still demonstrating custom live chart rendering.

frontend/widget.css

Main purpose: defines the look and feel of the widget and exposes brandable design tokens through CSS custom properties. 
.sr-widget-root {
    --sr-bg-color: #f4efe4;
    --sr-text-color: #241b14;
    --sr-primary-accent: #d06b2f;
    --sr-font-family: "Poppins", "Segoe UI", Roboto, Helvetica, Arial, sans-serif;
    --sr-border-radius: 22px;
    --sr-spacing: 18px;
}

.sr-widget-root[data-theme="dark"] {
    --sr-bg-color: #1a1713;
    --sr-text-color: #f3ead8;
}

Step by step

  1. It defines widget-level CSS variables for color, typography, spacing, borders, and shadows.
  2. It defines a dark theme by overriding variables rather than rewriting every component rule.
  3. It styles the match header, tab navigation, panels, tables, toolbars, forms, facts, comparison views, and status cards.
  4. It also styles the visible boot and tab error states added for reliability and testing clarity.

Why CSS variables are important here: they let operators change the widget appearance from outside the widget source, which is exactly what the specification asked for.

frontend/index.html

Main purpose: this is the example operator page. It proves how the widget is embedded and how it behaves in a surrounding page context. 
<div id="sr-widget-root"></div>

<script
    src="/static/loader.js"
    data-page-type="match"
    data-client="demo"
    data-match-id="12345"
    data-default-tab="table"
    data-theme="light"
    data-poll-interval-ms="5000"
></script>

Step by step

  1. It creates a simple host page with its own design language to simulate an operator website.
  2. It provides the widget mount root.
  3. It embeds the widget using a script tag with data-* attributes.
  4. It includes phase simulation controls that mutate window.__srMockStateOverride and call into the mounted widget instance.
  5. It also provides an auto-simulate mode so reviewers can watch the widget transition through match phases automatically.

Why this file matters: it demonstrates the integration story, not just the widget itself. That is important for an embeddable product interview.

configurator/config.html

Main purpose: this is the configuration and theming tool. It lets operators preview the widget, choose visible tabs, choose the default tab, tweak theme variables, and generate embed and CSS output. 
<select id="page-type-select" data-testid="config-page-type-select">
    <option value="match">Match</option>
    <option value="competition">Competition</option>
    <option value="homepage">Homepage</option>
</select>

<textarea id="embed-output" readonly data-testid="config-embed-output"></textarea>
<textarea id="css-output" readonly data-testid="config-css-output"></textarea>

Step by step

  1. The HTML creates a two-column layout: controls on the left, live preview and generated outputs on the right.
  2. The setup controls let the operator pick page type, homepage pinning behavior, visible tabs, and default tab.
  3. The branding controls let them choose accent colors, text colors, font family, radius, spacing, and theme mode.
  4. The preview area mounts a live widget instance so configuration changes are immediately visible.
  5. The embed output shows the script tag that a host page would use.
  6. The CSS output shows the variable overrides that control the look of the widget.
  7. The page JavaScript keeps the preview state coherent so that visible tabs, default tabs, and page-type rules remain valid as the controls change.

Why this file matters: it proves that theming and operator control were treated as part of the product, not just as an afterthought.
